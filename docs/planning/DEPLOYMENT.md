# Deployment, operations and cost model

Planning prices are in USD and were checked on 26 November 2026. The repo's current invoice is unknown. The pilot assumption is one paid Render web service with an attached disk, serving static pages and the live API on one canonical origin. An existing Render **static site** cannot simply start accepting WebSocket upgrades. Inspect the service type and prove a reversible same-domain routing or domain-transfer procedure first. Keeping the existing canonical origin is preferable if supported. If the assigned onrender.com hostname cannot transfer, keep the printable site live, test a controlled custom-domain migration with redirects/canonicals and obtain owner signoff before cutover. Pages remains available for the existing print workflow. GitHub describes Pages limits for commercial SaaS and transactions. ## Monthly cost sensitivity

Assume workspace base $0 in the example, an available 5 GB monthly outbound allowance, $0.15/GB beyond it, $0.25/GB-month disk. Starter compute $7, 1 CPU/2 GB $25, 2 CPU/4 GB $85. Recheck eligible workspace tier, taxes, domain, backup storage, monitoring, payment fees and actual included bandwidth before purchase. Approximate **incremental plan cost** = compute + disk + max(0, estimated outbound − available allowance) × unit rate + optional services. If existing usage consumes the allowance, the marginal cost increases. [Render pricing](https://render.com/pricing)

| Scenario/month | Workload assumptions | Compute + disk + egress | USD per month / per completion |
|---|---|---|---|
| Private pilot | 300 starts, 240 completes, 10 peak rooms × 6, 2 GB outbound | 7 + 1 GB × .25 + 0 | $7.25 / $0.0302 |
| Returning groups | 5,000 starts, 4,000 completes, 50 peak rooms × 6, 25 GB outbound | 25 + 5 GB × .25 + 20 × .15 | $29.25 / $0.0073 |
| Event stress envelope | 20,000 starts, 16,000 completes, 4 simultaneous 300-guest events plus 100 ordinary rooms × 6, 120 GB outbound | 85 + 10 GB × .25 + 115 × .15 | $104.75 / $0.0065 |

Egress inputs include static and live traffic. Estimate usage from traces by adding page visits × transferred assets, per-viewer snapshot bytes × sends and media bytes × authorized plays. Stress envelope is a load target, never a sales commitment. Staging at production size can double fixed compute. Hosting is usually a small expense beside translations, moderation, editorial work, refunds and event-day support. Model contribution per game in [monetization](MONETIZATION.md).

**Voice.** Eight seats × four 8 s clips × 32 kbit/s ≈ 1.024 MB recorded per match before overhead. At four plays per clip, 1,000 sessions add about 4.1 GB outbound. Hard byte cap at 32 × 256 KiB is 8 MiB/match, so reserve worst-case space, concurrent incomplete uploads and deletion time separately. Separate temporary media from snapshotted durable data. To establish deletion behavior and price, pilot a quota-limited ephemeral non-backed-up media directory with restart-to-gap UX. Private object storage with lifecycle expiry becomes justified if reliable replay across restarts or larger events is required. Record its storage/request/egress bill separately.

**AI.** Replay mode has $0 live inference cost. Editorial preparation costs occur before release. Record source/rights, usage and editor hours per pack. For optional live text use a *budgeting example*, $0.50/M input and $2/M output tokens, not a provider quote. A six-seat three-round match with one call per seat/round, max 600 total input and 150 output tokens/call costs at most 18 × (600×.50 + 150×2)/1M = $0.0108 before moderation/failed calls. At 80% completion that's $0.0135 per completed match. At eight seats it is $0.0144 per started match. 10k six-seat starts consume $108 before extras. Count retries in the same reservation, cap provider tokens (including billable reasoning if supported) and disable paid mode when reserve is insufficient. Hypothetical $30 monthly author-approved cap permits at most 2,777 such starts at the example rate before overhead. Default live allowance is zero. Pin an actual supported model, token semantics and current price before any purchase. Configure per-event, per-day and per-month ceilings and compare vendor bill to ledger. [Provider pricing](https://developers.openai.com/api/docs/pricing)

## Operator procedure and scale decision

1. Repository owner verifies hosting, region, domain and bill and declares maximum recurring spend. Measure mobile RTT from Vietnam and an international cohort to candidate regions. Choose one region for the pilot. Make build require an allowlisted PUBLIC_ORIGIN, production secret(s), disk path, protocol compatibility range and feature flags. Use fake keys only in a separate test environment.
2. In staging produce both a public HTML/JS/assets directory and a private server bundle. Validate root and Pages-prefix static paths, fresh node boot, read-only /health and readiness with DB migration checks. Bind Render's PORT on 0.0.0.0. Ensure proxies handle upgrades, session cookies and no-store room responses. Probe old pages after the staging build. Review permissions, disk mount and retention for every environment.
3. Before deploy, freeze new room creation and schedule a drain outside booked events. Notify existing clients, finish live rooms or snapshot for version-compatible resume. On SIGTERM reject new writes, finish in-flight commits, close sockets with retry signal and exit. Attached disks restrict horizontal scaling and zero-downtime deploy. Run additive migrations with a single owner, mark schema version, keep prior engine reader until room expiry. [Disk constraints](https://render.com/docs/disks)
4. On restart check DB integrity, scan deadlines, delete expired records before serving reads, then permit joins. For process crashes target zero acknowledged-action loss and reconnect within 30 s after readiness. Single-volume loss can forfeit recent ephemeral games. Explicitly close them with an expiry message. Do not restore previously revoked credentials, expired data or withdrawn clips. Backup persistent commercial entitlements separately when introduced. Proposed entitlement RPO 24 h and RTO 2 h, reconcile recent payments with provider receipts to avoid permanent purchase loss. Test an isolated restore before selling.
5. Track p95 commit-to-ack, event-loop delay, SQLite busy/lock duration, disk/WAL growth, bytes per recipient, memory, join/reconnect failures, cleanup age and cost/completion. Alert on sustained user-visible deadline misses, cleanup drift or budget-cap approach. Record runbook and on-call owner. Cap new rooms, coalesce display frames and turn off optional media first. Existing leases keep precedence.
6. Vertical scaling first if measurements show CPU/memory saturation. If booking requirements demand failover or single-writer contention remains after bounded snapshots, benchmark managed PostgreSQL with transactional row locks and room ownership/fencing. Route each room to a single current owner and resume from durable state. Add routing/pubsub only after a two-instance reconnect/failover test demonstrates need. Do not attach the SQLite volume to two writers. One 300-seat pass does not establish four-event capacity.
7. Roll back by disabling new rooms for the affected game, draining pinned matches, routing public traffic to the verified static artifact and reverting the app to the previous reader-compatible build. Never downgrade a live schema destructively. Restore data into a separate environment first, apply deletion/expiry policy, compare counts and receipts, then cut over deliberately.
