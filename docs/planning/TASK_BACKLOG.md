# Implementation task contracts

**Implementation awaits master-plan approval.** Each row plus its linked source is a standalone assignment. Give an agent the repository, its task ID, that row and the linked contracts. On every implementation task, use the audited main as a comparison, keep the legacy print workflow working, implement complete flows with a real server, and change only the assigned paths. The owner may grant a written scope extension. Run existing `npm test` plus the named checks. ## Parallel working agreement

One task per branch/worktree from the recorded contract commit, e.g. `git worktree add ../party-g4 -b game/g4-night-market <approved-sha>`. F1, F2 then F3 are ordered. P1 and A1 may run alongside F3 after F2. After R1 the independent game directories and native editing can proceed in parallel, subject to the developer's review capacity. Serialize package/lock/CI edits through F1's integrator. Game teams request a dependency with size, license and maintenance rationale. Reserve migration numbers with one DB owner. Keep shared type/event changes in a separate reviewed PR before rebasing dependent branches. Integrator alone edits public registry/catalog/sitemap. No hand edits to generated outputs unless repository convention explicitly requires tracking the output.

Once contract fixtures pass, merge to the integration branch and play a minimum-size match over real sockets. Review artifacts and projections, then record the evidence in a single integration commit before release. If an agent is interrupted, retain its branch and update its row with SHA, failing command/seed, completed artifacts, current blocker, next exact action and reviewer. On resume read [progress](PROGRESS.md), decision log, task contract and GDD, inspect changes since recorded SHA and rerun the last relevant command. Parallel tasks submit progress in PR descriptions for the integrator to consolidate, avoiding conflicts in the same ledger.
